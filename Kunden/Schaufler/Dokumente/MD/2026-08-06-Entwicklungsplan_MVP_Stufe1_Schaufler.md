# Entwicklungsplan_MVP_Stufe1_Schaufler

## Zusammenfassung
Technischer Entwicklungsplan für MVP-Stufe 1 des KI-gestützten Stücklistendatenerfassungs-Projekts bei Schaufler, basierend auf dem Lastenheft und Umsetzungsplan vom 05.08.2026. Enthält verbindliche Rahmenentscheidungen (Zwei-Phasen-Modellstrategie Azure OpenAI → gpt-oss-120b on-premise, Freigabe-Gate für Realdaten) sowie Sprint-0-Tickets zum technischen Fundament (Repository, Branching, Monorepo-Struktur).

SPRINT0-03 — Test-Strategie, Test-Pyramide, reproduzierbare KI-Tests über den Azure→On-Premise-Wechsel Kontext. AK 3–5 (Ableitung, Mapping, Aggregation) sind nur gegen ein Referenzset mit Ground Truth abnehmbar (Umsetzungsplan 1.1 zu Kap. 19; Teil 3 „Abhängigkeiten von der Konzeptphase”). Zusätzlich verlangt die Zwei-Phasen-Strategie, dass Tests den Provider-Wechsel überleben: Ein Testset, das an Azure-spezifischem Antwortverhalten hängt, wäre bei der Migration wertlos und würde MIG-03 (Regressionstest) unmöglich machen. Dieses Ticket definiert die Teststrategie als Dokument und als lauffähiges Gerüst. Umsetzung — Test-Pyramide (4 Ebenen). Unit (pytest, Ziel ~70 % der Testfälle): reine Logik — Normalisierung, Formatregeln (Härte, Kap. 12), Statusmaschine, Aggregation, Mapping-Funktionen. Kein I/O, kein LLM, keine DB. Integration (pytest + testcontainers): gegen echte PostgreSQL 17 mit pgvector (Container aus SPRINT0-08); Alembic-Migrationen laufen vor jeder Session; SMB-Zugriff gegen lokalen Samba-Testcontainer (BE-02). Pipeline-/E2E (pytest, markiert e2e): kompletter Wertstrom Dokument → Export gegen testdata/-Fixtures, LLM je nach Modus (s. u.), Excel-Ergebnis gegen Golden Files verglichen (zellweise, nicht binär). Qualitäts-Regression („Referenz-Testset”): annotierte Dokumente mit Soll-Stückliste (Ground Truth); Metriken Feldgenauigkeit (korrekt extrahierte Attributwerte / Soll-Attributwerte) und Positions-Recall (gefundene Soll-Positionen / Soll-Positionen) — exakt die Messgrößen der Konzeptphase (Umsetzungsplan Teil 3). SPRINT0-04 — CI/CD-Pipeline für Azure-Entwicklungsphase und On-Premise-/Air-Gap-Deployment Kontext. Zwei grundverschiedene Zielumgebungen: Phase 1 entwickelt online (Azure-LLM, Paketquellen erreichbar), das Endprodukt läuft aber on-premise, schlimmstenfalls air-gapped (Lastenheft Kap. 7.1 „externe Cloud-Abhängigkeiten ausgeschlossen”, Kap. 17 Bereitstellungsmodell; Air-Gap-Frage ist offener Punkt Prio-1 #3 des Umsetzungsplans). Die CI muss daher von Anfang an zwei Artefakttypen produzieren: schnelles Feedback für PRs und ein vollständig offline installierbares Release-Bundle. Wer erst zur Auslieferung „offline-fähig” wird, entdeckt versteckte Online-Abhängigkeiten (Modell-Downloads zur Laufzeit, Font-/Zertifikat-Nachladungen von PaddleOCR, pip-Installationen in Startskripten) zu spät. Entscheidung: GitHub (privates Repo) + GitHub Actions; ein selbstgehosteter Runner bei Prozessia mit GPU (DGX Spark aus der Konzeptphase) für OCR-/Modelltests und Phase-2-Jobs. Begründung: geringster Betriebsaufwand für ein kleines Team; der GPU-Teil ist ohnehin selbst zu hosten, egal welches CI-System. (Falls Prozessia intern GitLab betreibt, ist die Pipeline-Struktur 1:1 übertragbar — die Make-Targets kapseln alles; als ADR-Alternative dokumentieren.) Pipeline-Struktur. Workflow „pr” (jeder PR, Ziel < 10 min): lint → type → test (Unit+Integration, stub-Modus, Linux) → test-frontend (pytest-qt offscreen, Linux + Windows-Runner) → manifest-check (Testdaten-Governance) → secrets-scan (gitleaks) → build-smoke (Docker-Images bauen, nicht pushen). Workflow „nightly” (main, selbstgehosteter GPU-Runner): test-e2e (replay) → ocr-smoke (PaddleOCR-VL auf 3 Fixture-Scans, prüft nur Lauffähigkeit + Box-Ausgabe, keine Qualitätsschwelle) → quality (Ebene 4 live gegen konfigurierten Provider — Phase 1 Azure, nach MIG-02 vLLM) → Baseline-Report als Artefakt. Workflow „release” (Tag v*): 1. Alle pr+nightly-Jobs. 2. Air-Gap-Bundler (infra/bundle/make_bundle.py): Docker-Images (backend, db inkl. pgvector, vllm-Serving) als docker save-Tarballs; alle Python-Wheels via uv export + pip download in wheels/; Frontend-Installer für Windows (PyInstaller-Build, FE-01); Modellgewichte nicht im Bundle, sondern als separates, einmalig übertragenes Artefakt mit SHA256-Manifest (gpt-oss-120b ~60 GB MXFP4, PaddleOCR-VL ~2 GB — Bundle bleibt handhabbar, Gewichte ändern sich selten); Alembic-Migrationsstand; install.sh/install.ps1 + VERIFY.md (Checksummen-Prüfanleitung). 3. SBOM-Erzeugung (Software Bill of Materials, uv export --format requirements + syft über Images) — Update-/Versionierungsstrategie ist kritisches Kriterium in Kap. 17. 4. Offline-Installationstest: frische VM ohne Netz (Firewall-Regel im Runner), Bundle installieren, Smoke-Test (Health-Endpoint, Mini-Pipeline mit Stub-LLM) — der Beweis der Air-Gap-Fähigkeit, jede Release-Pipeline. Dieses Ticket liefert die davon sauber getrennte technische Beobachtbarkeit: strukturierte Logs, Korrelation, Metriken — so gebaut, dass (a) niemals vertrauliche Konstruktionsdaten in Techniklogs landen (Kap. 17 „Schutz vertraulicher Konstruktionsdaten”), (b) in Phase 1 jeder Azure-Aufruf nachvollziehbar ist (Kosten, Content-Filter, Latenz — von der Modellstrategie explizit als abzufedernde Unterschiede benannt) und (c) on-premise keinerlei Telemetrie nach außen fließt.
