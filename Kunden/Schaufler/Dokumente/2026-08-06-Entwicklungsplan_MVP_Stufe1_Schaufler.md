# Entwicklungsplan_MVP_Stufe1_Schaufler

## Zusammenfassung
Technischer Entwicklungsplan für MVP-Stufe 1 des KI-gestützten Stücklistendatenerfassungs-Projekts für Schaufler. Beschreibt verbindliche Rahmenentscheidungen (Zwei-Phasen-Modellstrategie Azure OpenAI → gpt-oss-120b on-premise), offene Freigabeklärung für Realdaten sowie Sprint-0-Tickets zum technischen Fundament (Repo-Struktur, Monorepo-Entscheidung).

SPRINT0-03 — Test-Strategie, Test-Pyramide, reproduzierbare KI-Tests über den Azure→On-Premise-Wechsel Kontext. AK 3–5 (Ableitung, Mapping, Aggregation) sind nur gegen ein Referenzset mit Ground Truth abnehmbar (Umsetzungsplan 1.1 zu Kap. 19; Teil 3 „Abhängigkeiten von der Konzeptphase”). SPRINT0-04 — CI/CD-Pipeline für Azure-Entwicklungsphase und On-Premise-/Air-Gap-Deployment Kontext. Zwei grundverschiedene Zielumgebungen: Phase 1 entwickelt online (Azure-LLM, Paketquellen erreichbar), das Endprodukt läuft aber on-premise, schlimmstenfalls air-gapped (Lastenheft Kap. 7.1 „externe Cloud-Abhängigkeiten ausgeschlossen”, Kap. 17 Bereitstellungsmodell; Air-Gap-Frage ist offener Punkt Prio-1 #3 des Umsetzungsplans). Die CI muss daher von Anfang an zwei Artefakttypen produzieren: schnelles Feedback für PRs und ein vollständig offline installierbares Release-Bundle. Wer erst zur Auslieferung „offline-fähig” wird, entdeckt versteckte Online-Abhängigkeiten (Modell-Downloads zur Laufzeit, Font-/Zertifikat-Nachladungen von PaddleOCR, pip-Installationen in Startskripten) zu spät. Entscheidung: GitHub (privates Repo) + GitHub Actions; ein selbstgehosteter Runner bei Prozessia mit GPU (DGX Spark aus der Konzeptphase) für OCR-/Modelltests und Phase-2-Jobs. Begründung: geringster Betriebsaufwand für ein kleines Team; der GPU-Teil ist ohnehin selbst zu hosten, egal welches CI-System. (Falls Prozessia intern GitLab betreibt, ist die Pipeline-Struktur 1:1 übertragbar — die Make-Targets kapseln alles; als ADR-Alternative
